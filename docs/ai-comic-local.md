# 本地 AI 漫画制作

在漫画工作区点击 **AI 制作漫画页**，可以把剧情或 NovelAI 提示词编排成漫画计划，逐区生成完整图片，再由本机 Python 识别和去除文字，把已确认的对白放回可编辑文字层。

故事编排和图片生成使用当前登录的 NovelAI 账户。文字识别、去字和文字层重建在本机执行。第一版保留生成图片里的气泡外观；不检测或裁切实际分镜，也不把气泡转换成矢量元素。已有画框和角色位置用于编排提示，不能作为生成结果的真实几何位置。

## 安装和首次准备

1. 更新源码后，先停止本项目的旧服务，再运行根目录 `setup.bat` 安装依赖并重新构建前端。运行 `start.bat` 后登录本地工作区。启动器会检查并复用已有的同项目服务，不需要另外启动一套前后端。
2. 在 **漫画制作** 中新建页面并选择布局。保持单框时由 AI 按剧情自由安排分镜，通常以 5–8 格为目标；也可以先选择模板或手动画出多个参考分镜。
3. 首次“一键制作”会先下载并加载本地文字模型，额外下载约 **303 MB**。下载和校验通过后才进行编排及生图，避免付费生成完成后才发现本地依赖缺失。

所需 Python 依赖写在 `nai_flask/requirements.txt`：

| 依赖 | 项目要求 | 用途 |
| --- | --- | --- |
| Python | 3.11 或以上 | 后端运行环境；CI 使用 3.11 |
| NumPy | `>=2.2,<3` | 图片数组处理 |
| Pillow | `>=11,<13` | 图片读写与透明通道 |
| ONNX Runtime | `>=1.24,<2` | CPU 模型推理 |
| RapidOCR | `3.10.0` | 文字检测、方向分类和识别，附带固定 OCR 权重 |
| OpenCV Headless | `4.14.0.94` | 字形蒙版与局部图片处理 |

本功能固定使用 CPU。电脑配置了 GPU 版反推或放大时，漫画文字任务仍使用 CPU。手机访问本地工作区时使用的是电脑的模型和算力，不会在手机浏览器下载或运行模型。

## 四种布局和 32 像素留白

新建漫画页在每个生成区域四边保留 **32 px** 留白。模型只生成内容区，图片返回后放入内容区；对白坐标也按内容区换算。

| 布局 | 最终画布 | 每次生成图片 | 图片数量 |
| --- | --- | --- | ---: |
| 竖版 | 896 × 1280 | 832 × 1216 | 1 |
| 横版 | 1280 × 896 | 1216 × 832 | 1 |
| 双列 | 2560 × 896 | 左、右各 1216 × 832 | 2 |
| 双行 | 1280 × 1792 | 上、下各 1216 × 832 | 2 |

双列和双行会一次编排两个连续故事区域，再逐张生成；每个区域都有自己的四边留白，因此中间相邻的两侧留白合计为 64 px。两次生图之间沿用 15 秒间隔。旧漫画项目保留原画布尺寸，不会因为新建页默认尺寸变化而被拉伸。

多个可见普通画框会按阅读方向整理为参考分镜，叠加画框不参与编排参考。参考分镜提供编号、位置和尺寸；生成后的完整图片会替换目标区域的旧排版。生成图片中的实际画框可能与参考不同，系统不会按旧画框切图。

## 制作和修改流程

1. 点击 **AI 制作漫画页**，直接粘贴一条 NovelAI 生图提示词，或输入一句剧情。AI 负责提取人物和台词、扩展故事、安排分镜和角色坐标；不要求用户先写分镜脚本。原提示词中的画师及权重、画风、人物身份和已有台词需要继承。
2. **高级补充（可选）** 默认折叠。人物与画风可以留空，只有输入完全没有风格时才采用黑白漫画。对白语言（中文、英文或日文）控制新写的台词；输入中明确给出的台词保留原文。制作分为两阶段：写作模型先扩展剧情、对白和镜头节奏，**GLM 4.6** 再整理结构与角色坐标。有效 Opus 订阅的新任务默认使用 **Xialong v1** 写作，其他订阅使用 GLM 4.6；已有草稿保留用户选择。可用权限和生成费用以官方账户返回为准。
3. 点击 **一键制作** 完成整个流程。也可先点 **仅编排**，展开可选的计划编辑器检查摘要、分镜、人物、坐标和台词，修改后点 **继续未完成步骤**。原生提示词中的 `4koma` 等布局标签原样保留；手工参考分镜优先用于定位，但模型采用不同格数不会因此停止生图。
4. 每个区域通过现有 V5 生图流程生成一张完整图片。同一个人物在不同分镜中使用独立角色实例；同一分镜中的两个人分别设置角色提示词和位置。一个区域最多 22 个角色或场景控制实例。对白单独保存，发起生图时再写入最终请求，避免修改后同时夹带旧台词。
5. 原图返回后先保存，再进行本地文字处理。自动识别出的文字与计划台词进行一对一匹配；只有对应关系确定的文字才会去字并变成编辑元素。
6. 在画布中选中文字，可继续改字、调整位置、大小、颜色和书写方向。气泡的轮廓和背景仍属于整张底图。原图另存为默认隐藏、锁定的 **AI 生成原图** 图层，便于对照。
7. 保存漫画页；用 **导出项目** 保存可继续编辑的项目包，用 **导出 ZIP** 输出按页排列的 PNG。浏览器草稿不是跨设备备份，换浏览器、电脑或访问地址前应先导出项目。

计划编辑器中的角色中心代表生图控制位置。文字重建的位置来自原图检测结果，不会把角色中心或参考画框坐标当作真实对白位置。

没有参考分镜时，写作模型先输出“整页分镜设计”，说清视觉重心、主格与小格的大小关系、画框穿插和阅读动线，再写连续编号镜头。通常以 5–8 格为创作起点，根据剧情增减，不是数量门槛。纵向主格、窄条、斜切、重叠插格、破框和留白按故事选用，不固定组合或套成 1-2-1-2。结构整理阶段把设计明确写入 `globalPrompt`，用英文 Danbooru 标签配合自然语言描述主次、形状和画面关系；每格镜头也使用适合的景别、机位、动作标签。剧情、台词和最后的可见收尾属于创作要求，程序不再按覆盖率决定是否准许生图。

整理阶段为每次可见人物出场分别编写英文提示词，保留该镜头的动作、表情、视角和裁剪要求。生成时程序为每个角色槽带上对应的固定外观，再接该次出场的镜头提示；角色外观不会只留在计划元数据中。同一人物跨格不会合并为一个角色槽，双人镜头也不共用一个槽。空镜直接描述场景和道具，不再强制每格安排角色槽。画外音保留真正的说话人，但不会为了满足校验而把说话人强行画进镜头；对应文字通过主提示词描述画外气泡，并进入最终 `Text:` 清单。

分镜边界和格内人物坐标只用于换算整图角色控制坐标，不会转成百分比、精确宽高或坐标句子塞进绘图提示词。提示词要求模型尽量给出符合版式设计的粗略边界；合法边界内缺少人物中心时，按同格人数与阅读方向排位。缺失或非法分镜边界不再报错，也不补一个规则网格强制控制人物，改由图像模型按画面提示自行排位。主提示词仍明确描述宽窄、高矮、跨行、叠压、斜切和边框关系；“不写精确比例”不等于省略分镜设计。每格英文镜头描述会加入主提示，有真实规划边界时才附加粗方位。规划数据不能当作实际画框检测结果。

### V5 权重与负面提示词

采用 NovelAI 自己的 `n::内容::` 数值语法，负权重为 `-n::概念::`，不限于 `-1`；例如 `1.3::dynamic perspective::`、`-3::4koma::`、`-2.5::static composition::`。这些是语法示例，不是每页固定追加的词。每组用 `::` 结束，不使用 `(tag:1.3)`。用户原来的权重和版式标签原样保留，不再删除未加权的 `4koma`、`split screen`、`no text`，也不再追加固定负权重或 UC。需要时由模型按本页设计选择排除对象与强度；用户明确要四格或网格时应尊重。Undesired Content 可用正数权重加强排除。

默认布局引导不排除 `comic`、`multiple views`、文字、气泡或黑白风格，也不全局禁止正面和特写——它们都是合理漫画镜头。每个角色槽还可以有自己的负面提示，针对该人物的错误服装、视角或动作。漫画默认使用 V5 Full 的自定义负面提示，不混入会压制多镜头的 Heavy 预设。

2026-10-19 核对的官方依据：[数值与负数权重](https://docs.novelai.net/en/image/strengthening-weakening/)、[角色提示和位置控制](https://docs.novelai.net/en/image/multiplecharacters/)、[Undesired Content 与各模型预设](https://docs.novelai.net/en/image/undesiredcontent/)。负数权重支持 V4.5 及以上；V5 最多 22 个角色控制槽。这些语法可以引导结果，不能保证每张生成图都满足构图要求。

### 保留哪些检查

保留模型权限、输入区域尺寸、能读取的完整回复与 JSON、可用生成区域、V5 最多 22 个角色槽和实际文字容量等执行边界。缺句、重复、改写、未知台词编号、未知说话人、空镜、缺省数组、格数差异及不完美坐标不再阻断生图。模型直接返回的 `text` 优先；没有文字时才通过有效 `sourceId` 取原句，无文字可用的条目略过，不擅自补写缺失剧情。也不再把 UTF-8 字节数当 token 数，按保守估算阻断中文素材；保留完整输入，由上游处理真实上下文限制。OCR 的不确定匹配、生成失败保留原图和防止覆盖新编辑仍保留，避免误擦已有画面。

已取消说话人必须入镜、每格必须有角色槽、无参考框必须七格、原始台词必须原顺序、视觉提示中出现相同引号台词就直接报错等限制。模型返回一个完整 JSON 代码围栏时可以正常解析；仍不会补写截断 JSON 或猜测缺失的剧情。

原生提示词先按大小写不敏感的 `Text:` 分离视觉提示和台词，空行分隔台词，字面的 `\n` 转成换行。画师、权重与布局标签原样保留。写作原文与使用的模型可在计划中折叠查看，并随项目保存。结构整理阶段可以引用原始台词编号，也可以直接写台词；程序生成稳定编号、阅读顺序和有依据的人物坐标，标题放入首格。原始输入仍保存在项目中。已移除固定五格示例，避免用示例版式影响自由设计。

## 核对文字与重试

面板中绿色框表示已成功去字并建立可编辑文字；橙色框表示保留了原图文字。重复短句、OCR 不确定、没有找到对应台词或与待核对文字重叠的区域不会自动擦除。

- 对橙色区域选择正确的 **对应台词**，再点击 **仅重建文字**。每条台词只能分配给一个文字块；不要靠阅读顺序猜测重复的“嗯”“好”等短句属于谁。
- 选择 **保留原文字，不改写** 会明确保留该区域，后续重建也不会自动匹配并擦除它。
- 文字重建始终重新读取同一张原图，不会在上一次去字底图上继续识别。可以修改计划台词后只重建文字，无需再次生图。
- **重新生成本区（消耗额度）** 会重新请求图片。它与“仅重建文字”是两个不同操作。
- 漏检文字不会自动创建可编辑层；可以使用现有画布文字工具手动补字，并根据原图实际情况调整。人工选定对应关系也不能保证复杂背景的去字效果，应检查结果。

如果处理期间修改了目标区域，新结果会留在面板中显示 **待应用**，由用户点击 **替换本区当前内容（可撤销）** 后再写入画布。切换到其他页不会把在途结果写到当前页。

**停止后续步骤** 会停止尚未发起的生图和本地处理；已经发出的图像请求返回后仍先保存结果。ONNX 推理会收到终止请求；OCR 调用或模型加载需要等当前调用返回后检查取消。取消下载保留可续传的 `.part` 文件。

刷新浏览器或重启后端可能中断当前制作流程。重新生成前先查看本地图库和项目中是否已经保留原图，避免重复生成。缺少原图时不能执行“仅重建文字”。

CTD 和 LaMa 额外下载合计 **302,714,572 字节**。即使当前图只有纯色气泡，首次准备也会下载完整模型组；LaMa 会在需要复杂背景修复时才加载到内存。来源许可分别为 CTD 的 GPL-3.0 和 RapidOCR、LaMa 的 Apache-2.0，分发模型或修改代码时应同时保留对应许可要求。

模型清单及下载文件的 SHA256 位于 `nai_flask/api_utils/inference_models.json`。OCR 随包权重的大小和 SHA256 位于 `nai_flask/api_utils/comic_lettering.py`；首次使用会校验固定文件，不运行来源仓库里的 Python 代码。

模型目录沿用 `inference_models_dir`，未设置时使用 `data_dir/models`。漫画模型缓存位于 `comic-lettering/<固定版本>/`。修改目录需重启后端；配置方式见 [本地推理配置](local-inference.md)。不要把本地配置、账户资料、输出图片或模型缓存提交到仓库。

同一后端一次只运行一个本地推理任务，与提示词反推、放大共用任务队列和释放机制。模型下载、校验、识别和去字阶段分别显示进度。

原图、清理后的底图和擦除蒙版会保存到本地图库。底图和蒙版的元数据记录 `comic_lettering_source_hash`，用于对应原图像素；原图文件不被覆盖。漫画项目另行保存计划、原图、底图、蒙版、文字块和人工对应关系，项目包导入后仍可继续编辑。

纯色背景使用附近背景色填充字形，并补齐文字框内 CTD 漏掉的细小笔画；复杂背景交给 LaMa 修复。写回时只采用实际擦除蒙版覆盖的像素，其他像素和透明通道保留。蒙版不会代表整块气泡或整格画面。

## 文字编排接口与协议依据

写作和结构整理分别向 `https://text.novelai.net/oa/v1/chat/completions` 发送一次请求，使用字符串 `messages`、`stream: true`、`enable_thinking: false` 和 `Accept: text/event-stream`。第一阶段返回完整写作正文，第二阶段接收该正文与原始约束并返回 JSON 计划；不自动循环修复或重发。本地日志和诊断文件的关联编号分别带 `-story` 和 `-format` 后缀，上游 `X-Correlation-ID` 请求头仍只发送六位字母数字。后端收齐 SSE 中的 `choices[].delta.content` 或 `choices[].text`，再解析和校验完整漫画计划后返回前端。上游仍返回 JSON 时兼容 `message.content` / `text`；缺失正文时不猜测解码 `token_ids`。

采用 SSE 有实际故障和开源实现依据：2026-10-19 的非流式请求返回 HTTP 200，`text` 为空，响应存在 `token_ids` 字段，`usage.completion_tokens` 为 672。本次没有保存原始 `token_ids`，因此没有恢复该次编排，也不能声称可直接离线恢复。此故障发生在编排阶段，尚未发起生图。

2026-10-19 核对的协议来源：

- [NovelAI 官方接口定义](https://text.novelai.net/docs/doc.json)分别提供 `/oa/v1/chat/completions` 和 `/oa/v1/completions`，支持 `stream` 与 `enable_thinking`。官网编辑器的 raw completions 路径使用编码后的 `prompt` token 数组，收到 `token_ids` 后由本地 tokenizer 解码；可核对当前构建的[端点常量](https://novelai.net/_next/static/chunks/2rdp03_8cyuh_.js?dpl=b50892a-38995131626-1)和[生成与解码代码](https://novelai.net/_next/static/chunks/0wi7fejx317_y.js?dpl=b50892a-38995131626-1)。这是官网 `/completions` 路径的处理方式，不能据此把 `/chat/completions` 的字符串消息改成 token 数组。
- **NekoAI-JS v1.3.0（2026-07-17）**：[chat 实现](https://github.com/Nya-Foundation/NekoAI-JS/blob/61c177721b1177d2a34bdce15de3eada1160d2f9/src/client.ts#L784-L849)明确记录非流式聊天可能只返回原始 token ID，因此改用 `chatStream()` 并聚合 `delta.content`。[消息与流解析](https://github.com/Nya-Foundation/NekoAI-JS/blob/61c177721b1177d2a34bdce15de3eada1160d2f9/src/client.ts#L893-L925)只包装消息和解析 JSON；底层 [SSEStream](https://github.com/Nya-Foundation/NekoAI-JS/blob/61c177721b1177d2a34bdce15de3eada1160d2f9/src/utils/http-utils.ts#L39-L81)中的 `TextDecoder` 处理网络 UTF-8 字节，没有模型 token 解码。
- **NovelAI-LLM-Proxy（2026-05-21 快照）**：[请求构造](https://github.com/TheSmilingPony/NovelAI-LLM-Proxy/blob/46b4f1cc6baa82a56608aba197a00e9d6f111c54/proxy.py#L533-L585)对普通 JSON 客户端也强制上游流式；[文本提取](https://github.com/TheSmilingPony/NovelAI-LLM-Proxy/blob/46b4f1cc6baa82a56608aba197a00e9d6f111c54/proxy.py#L172-L189)兼容 `delta.content`、`text` 和 `message.content`。它仅在请求 logprobs 时转换为 `prompt`，本项目没有该需求。

### 连续任务卡顿的原因和修复后记录

浏览器集成验收中，同一张 832 × 1216 合成图第一次处理成功，随后仅改变文字方向再次重建时，CTD 检测阶段出现分钟级耗时。独立进程按相同的“加载 → 处理 → 再加载 → 再处理”顺序复现，堆栈停在 CTD 的 ONNX 卷积执行；未修复配置超过 120 秒仍未完成检测。

## 服务器迁移前置项（本轮不实施）

当前实现面向本地开源版，未连接服务器、安装远端依赖或修改任何线上进程。迁移前需要单独确认：

- 目标系统的 Python 版本与 ONNX Runtime、RapidOCR、OpenCV Headless 兼容，CPU、内存和模型磁盘空间满足实际图片负载；先在独立环境完成同样的合成诊断和真实图片验收。
- 固定模型下载源可达，或提前放置通过同样大小与 SHA256 校验的文件；运行用户能够读模型目录、写输出和临时目录。模型缓存和业务图片分开管理。
- 多进程、多 Worker 或多用户部署的任务占用、取消、归属、进度轮询与结果保存需要专门评估；本地当前的单任务内存状态不能直接视为跨进程队列。
- 现有后端会话、来源校验、账户权限和生图计费限制保持有效；需要明确公开访问边界和结果文件权限，不能直接把个人本地服务暴露到公网。
- 部署前列出具体配置、依赖安装命令、托管项目、启动用户、目录权限、停止与启动顺序、回退版本和验证步骤。涉及宝塔托管服务时使用宝塔管理方式，维护面板状态与进程一致。
- 若未来接入服务器现有 V5 私有结果交付，API 与所有 Worker 必须确认同一绝对结果目录、同一共享文件系统及兼容的读写权限；这些属于迁移预检，不是本地实现已完成的能力。
